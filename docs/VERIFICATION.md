실제 앱 모듈을 최소 DOM·저장소 모의 환경에서 실행했다. 실제 브라우저 저장소를 강제로 차단한 검증은 아니다.

## 실제 브라우저 흐름

- 한식·10,000원·순한맛 선택 후 예상 메뉴 3개 표시.
- 추천 결과가 후보 안에 있으며, 재추천 시 직전 메뉴와 달라짐.
- Escape로 추천을 취소하면 기록이 증가하지 않음.
- 불고기 덮밥 두 번 확정 후 기록은 1개, 중복 안내 표시.
- 새로고침 후 필터 3개와 기록 1개 복원.
- 검색으로 1개 후보만 남기면 재추천 버튼 비활성화.
- 그 후보를 제외하면 빈 결과 안내 및 추천 버튼 비활성화.
- 제외 목록에서 복원하면 다시 후보에 포함.
- 새로 추가한 빈 결과의 직접 복원 버튼으로 후보 1개 복구.
- 기록 2개 중 1개 삭제 후 남은 삭제 버튼의 `tabindex=-1` 문제 발견. 수정 후 `tabindex`가 없는 기본 버튼으로 유지되는 것을 확인.
- 375 × 812 화면에서 문서 너비 375px, 1280 × 1000 화면에서 문서 너비 1280px: 가로 넘침 없음.
- 모바일에서 분식·7,000원·순한맛 선택 → 김밥·찐만두 표시. Enter로 추천 창 열기 및 Escape로 닫기 확인.
- 브라우저에서 수집된 error/warn 로그 없음.
- 검증용으로 생성한 선택 기록은 UI에서 삭제하고 필터를 초기 상태로 복구.

## 미리보기 서버와 공개 배포

로컬 미리보기 서버의 변경 후 `/`와 `/src/core.mjs`는 HTTP 200, 인코딩된 상위 경로를 이용한 `.git/config` 요청은 HTTP 404임을 확인했다.

GitHub API에서 `Baw-Appie/oneul-menu`의 공개 범위가 `PUBLIC`, Pages 상태가 `built`임을 확인했다. 공개 주소 `https://baw-appie.github.io/oneul-menu/`를 브라우저에서 열고 한식·10,000원·순한맛 조건으로 추천을 실행해 돼지국밥과 해당 조건 표시를 확인했다. 공개 주소에서 수집된 error/warn 로그도 없었다. 이후 필터를 초기화했다.

## v3 네 기능 통합 검증 — 2026-10-27

### 기능별 채팅과 로직 검증

사용자 요청에 따라 기능별 채팅 네 개에 `gpt-6.1-sol`과 `xhigh`를 지정했다. 생성 도구에는 Fast 설정 항목이 없어 적용 여부를 확인하지 못했다. 초기 용량 부족으로 중단된 메뉴 비교 채팅은 같은 모델로 재시도했다. 각 채팅은 담당 모듈과 문서만 커밋했다.

- 최근 메뉴 제외: [기록](RECENT_MEALS.md), 15개 그룹. 6개 시간대와 자정·월말·연말·윤년·DST, 미래·손상 기록 검증.
- 즐겨찾기: [기록](FAVORITES.md), 9개 그룹. ID 검증·중복 제거·불변 토글·후보 순서·버튼 접근성 속성 검증.
- 두 메뉴 비교: [기록](MENU_DUEL.md), 순수 함수 6개 및 모의 DOM 9개 그룹. 서로 다른 두 후보의 균등 추출·후보 갱신·오래된 선택 차단·파괴 후 이벤트 정리 검증.
- 기록 요약: [기록](HISTORY_SUMMARY.md), 19개 그룹. 기간 경계·중복·미래·잘못된 날짜·공동 1위·안정 정렬·최근 7건 렌더링 검증.

통합 채팅에서는 표준 입력 Node assert로 종류 7 × 예산 4 × 매운맛 4 × 최근 제외 3 × 즐겨찾기 2 = **672개 후보 조합**을 독립적인 기대값과 대조했다. 기존 버전 저장값에서 기록을 보존하고 신규 설정을 기본값으로 복원하는지, 손상된 즐겨찾기·필터를 정리하는지 확인했다. AI 요청에는 문장과 현재 후보 ID만 들어가며 기록과 즐겨찾기 목록은 포함하지 않는지, 취소한 세션의 늦은 응답을 무시하는지도 검증했다. 요약 기간·공동 순위 및 두 후보 추출의 난수 구간 분할도 별도 확인했다.

### 실제 브라우저 통합 흐름

Node.js v24.11.0과 Codex 내장 브라우저로 확인했다. 기본 서버는 키를 로드하지 않고 `127.0.0.1:4175`에서 실행했다.

- 비빔밥·돈카츠 즐겨찾기 → 즐겨찾기만 선택 시 두 카드만 표시.
- 두 메뉴 비교 → 비빔밥 고르기만 하면 기록 0개 → 기존 결과창에서 확정하면 1개.
- 최근 3일 제외 → 방금 확정한 비빔밥이 사라지고 돈카츠만 남음. 한 후보 비교창은 카드 하나와 안내, 재비교 비활성화 표시.
- Escape로 비교창을 닫은 후 비교 버튼으로 포커스 복원. 새로고침 후 최근 3일·즐겨찾기 2개·선택 기록 1개·후보 돈카츠 복원.
- 남은 후보의 즐겨찾기를 해제하면 후보 0개, 추천·비교 비활성화. 사라진 버튼 대신 ‘전체 메뉴’ 필터로 포커스 이동.
- ‘최근 먹은 메뉴 다시 포함’으로 후보 1개 복원. 즐겨찾기를 모두 해제한 빈 결과에서는 ‘즐겨찾기 밖 메뉴도 보기’로 전체 30개 복원.
- 돈카츠까지 확정하면 선택 2회·서로 다른 메뉴 2개·기록한 날짜 1일 및 한식·일식 공동 1위 표시.
- 여러 후보에서 ‘다른 후보 보기’는 직전과 다른 조합 표시. Enter로 비교창 열기, Tab으로 닫기 버튼 이동, Escape로 닫기 확인.
- 같은 메뉴를 다시 확정하면 기록 개수 유지. 목록을 다시 그린 뒤에도 비교 버튼으로 포커스 복원.
- 검색을 비빔밥으로 제한하고 최근 7일 제외 시 후보 0개 → 해당 기록 삭제 후 후보 1개 복원 및 요약 즉시 감소.
- 검증용 선택 기록과 즐겨찾기를 UI에서 제거하고 필터를 초기화해 메뉴 30개·기록 0개·즐겨찾기 0개로 복구.

### 모의 AI 서버를 이용한 실제 UI 검증

실제 OpenAI 호출과 구분하기 위해 표준 입력으로 임시 로컬 HTTP 프록시를 실행했다. 정적 자원은 실제 서버에서 가져오고 `/api/search`만 모의 응답으로 처리했다. 테스트 파일·패키지·API 키를 추가하지 않았으며 검증 후 모의 서버와 탭을 종료했다.

- 비빔밥·돈카츠 즐겨찾기, 비빔밥 선택 기록, 최근 3일 제외를 겹치면 요청 후보는 `pork-cutlet` 하나뿐이며 화면도 돈카츠 1개.
- 요청 본문의 키는 `query`, `candidateIds`뿐임을 서버에서 확인.
- AI 결과의 돈카츠를 확정하면 기록 2개·후보 0개로 바뀌고 AI 결과 및 해제 버튼이 초기화됨.
- 5초 지연 검색 중 즐겨찾기 필터 변경 → 로딩 해제·후보 30개 → 지연 응답이 도착한 이후에도 결과가 덮어쓰이지 않음.

- 실제 OpenAI API 호출은 이번 v3 작업에서 재실행하지 않았다. 기존 v2의 실제 호출 검증과 위의 모의 통합 검증을 구분한다.
- 실제 자정까지 기다려 30초 주기·탭 복귀의 날짜 갱신을 확인하지는 않았다. 기간 계산은 시간대별 순수 함수 검증으로 확인했고, 자동 갱신 연결은 코드 검토했다.
- 실제 스크린 리더·휴대폰 및 Chrome/Safari/Firefox별 교차 검증은 수행하지 않았다.

## Docker 배포 검증 — 2026-10-29

호스트 Node.js v24.11.0, Docker CLI 29.8.2, Docker Compose 5.6.0과 Colima의 Docker Engine으로 확인했다. 빌드한 `node:24-alpine` 컨테이너의 Node.js는 v24.22.2였다. 실제 `.env`나 API 키를 읽거나 출력하지 않고 빈 키와 `.env.example`을 사용했다. 검증 스크립트는 표준 입력으로만 실행했으며 테스트 파일·패키지는 추가하지 않았다.

### 설정과 서버 회귀 검증

- `docker compose --env-file .env.example config --quiet` 통과.
- Compose JSON을 표준 입력으로 검사해 기본 포트·바인딩·빈 키·읽기 전용·init 설정, `APP_PORT=8180`과 `BIND_ADDRESS=127.0.0.1` 설정, 별도 HTTPS 도메인 설정을 확인했다. 사용자 키가 출력될 수 있는 기본 `config` 출력은 사용하지 않았다.
- 실제 `createSearchRoute`에 모의 요청·응답과 모의 검색 함수를 연결한 **44건**이 통과했다. 기존 localhost/127.0.0.1 접근, 키 미설정 503, 메서드 제한, HTTP·HTTPS·별도 포트·IPv6 주소, 허용 Origin의 POST 성공, 다른 Host·Origin·Fetch Metadata 거부, 전달 헤더로 우회 불가, 잘못된 배포 주소의 시작 시 거부를 확인했다. 실제 OpenAI 호출과 구분한다.
- `node --check server.mjs`, `node --check server/search-route.mjs`, `git diff --check` 통과.

### 이미지와 실제 컨테이너 검증

- `docker build --pull -t oneul-menu:deployment-check .` 성공. Compose도 별도 프로젝트 `oneul-menu-deployment-check`에서 `up -d --build --wait`로 실제 빌드·기동해 `healthy` 상태를 확인했다.
- 호스트의 `127.0.0.1:14173`에만 공개하고 `APP_ORIGIN=https://menu.example.com`, 빈 키를 설정했다. 컨테이너는 UID 1000으로 실행되며 `/app`에 쓰기를 시도하면 `EROFS`가 발생했다.
- 이미지의 `/app`에는 `server.mjs`, `index.html`, `styles.css`, `server/`, `src/`, `assets/`만 존재했다. `.env`, Git 이력, 문서와 Docker 설정은 포함되지 않았다.
- `/`의 GET·HEAD, `styles.css`와 `src/`·`assets/`의 모든 파일이 HTTP 200이었다. `.env`, `.git/config`, 서버 소스, 문서, Dockerfile, 인코딩된 상위 경로 요청은 HTTP 404였다.
- 실제 HTTP 요청에서 허용된 HTTPS Host·Origin은 API 상태 200, 다른 프로토콜·Host·cross-site 요청은 403, 빈 키의 POST는 503이었다. 호스트에서도 공개 포트에 원래 Host·Origin을 전달해 상태 200을 확인했다.
- 같은 Compose 프로젝트를 `APP_ORIGIN` 미지정 설정으로 재생성해 다시 `healthy`를 확인했다. `APP_PORT=14173`이 기본 Origin `http://localhost:14173`에 반영되며 해당 주소의 API 상태가 200이었다.
- 검증 후 임시 Compose 컨테이너와 네트워크는 제거했다. 빌드한 로컬 이미지는 남겨 두었다.

### 이번 검증의 한계

- 실제 도메인·DNS·TLS 인증서·리버스 프록시는 배포하지 않았다. HTTPS Origin 처리는 HTTP 요청의 헤더와 서버 검사로 검증했다.
- 실제 OpenAI API는 호출하지 않았다. UI가 바뀌는 작업이 아니므로 브라우저 흐름도 재검증하지 않았다.
- 다중 서버 운영, 영속 사용량 제한, 인증, 장애 후 자동 복구와 장시간 부하 검증은 수행하지 않았다. 런타임 이미지 태그는 이동하므로 이후 빌드의 정확한 패치 버전은 달라질 수 있다.

## 공통 한계

- Chrome·Safari·Firefox 각각에 대한 별도 교차 검증과 실제 휴대폰 검증은 하지 않았다.
- 모든 메뉴의 실제 식당 가격·레시피·매운맛을 검증한 서비스가 아니다. 예시 데이터다.
- 저장소 차단과 손상은 모의 환경 및 복원 함수로 검증했다.
- 여러 탭의 동시 변경, 계정 간 동기화, 서버 저장은 이번 범위에서 제외했다.
